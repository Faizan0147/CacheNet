## 2. Round-trip time (R6)

ICMP ping to H1 and H2 is blocked by their Windows firewalls (100% loss), so RTT is measured at the transport layer: `connect()` returns when the SYN-ACK arrives, i.e. after exactly one round trip.

- TCP connect H3 -> H2: mean **7.00 ms ± 2.09 ms** (median 6.45 ms, n = 10).
- CNTP round trip (HEAD of a cached object on an open connection): mean **7.65 ± 2.55 ms** (median 6.93 ms).
- Application processing at the proxy ≈ CNTP RTT − TCP RTT = 6.93 − 6.45 = **0.48 ms** (medians; parsing, cache lookup and building the reply in Python).
- RTT used in the delay model below: median TCP connect = **6.45 ms**.

## 5. Explaining the results with the nodal delay model (Lecture 02)

d_nodal = d_proc + d_queue + d_trans + d_prop, summed over every node a packet passes through.

**Propagation.** d_prop = d / s = 10 m / 3×10⁸ m/s = **33 ns** per hop, ≈ 0.13 µs for a full round trip through the AP (4 hops). Negligible against a 6.45 ms RTT, so on a LAN the RTT is made of processing, queueing and transmission, not distance.

**Transmission, small messages.** A 111 B request frame: L/R = 111×8 / 72.2×10⁶ = **12.3 µs**. Also negligible, so the 6.45 ms RTT is mostly 802.11 medium access (contention back-off, AP forwarding, power-save wake-ups) = processing + queueing at the AP and hosts.

**Transmission, large object.** /large.txt is 205,201 B on the wire (CNTP + TCP/IP + Ethernet headers, measured with tshark). One air transmission: L/R = 205,201×8 / 72.2×10⁶ = **22.74 ms**. Via the AP it crosses the air twice, so the ideal is 45.47 ms (an upper bound of R/2 = 36.1 Mbps for host-to-host goodput).

**Large HIT decomposed.** Measured median 104.17 ms = TCP handshake (1 RTT) + request until first byte (≈1 RTT) + data transfer. Transfer ≈ 104.17 − 2×6.45 = **91.26 ms**, i.e. an effective goodput of 200,095×8 / 0.0913 s = **17.54 Mbps**, about 49 % of the R/2 ideal. The gap is (i) 802.11 MAC overhead (contention, per-frame ACKs, preambles; real 802.11n efficiency is roughly 50–70 % of PHY rate) and (ii) TCP slow start: 138 segments of 1460 B starting from a 10-segment window need ≈4 round trips (10+20+40+80…), adding ≈4×6.45 = 25.81 ms.

**Large MISS vs HIT.** MISS median 250.43 ms − HIT median 104.17 ms = **146.26 ms** extra. On a miss the proxy opens a TCP connection to H1 (1 RTT), sends the request (1 RTT), and must receive the *whole* 200 KB before it forwards anything (it stores the object in the cache first). This is store-and-forward, exactly like the transmission delay of a router: the object is transmitted twice in sequence (H1→H2, then H2→H3). Predicted extra ≈ 2 RTT + one more transfer = 2×6.45 + 91.26 = **104.17 ms**; the remaining 42.10 ms is processing at H1/H2 (Python reading the body in 4 KB chunks and copying it) plus queueing. The MISS spread (SD 56.83 ms vs 5.37 ms for HIT) is larger because two Wi-Fi transfers queue instead of one.

**Small MISS vs HIT.** 28.42 − 14.12 = **14.30 ms** ≈ 2 RTT between proxy and origin (connect + request); transmission of a 29 B body is negligible. Implied proxy↔origin RTT ≈ 14.30/2 = 7.15 ms, consistent with the 6.45 ms client↔proxy RTT measured directly.

**Persistent vs non-persistent.** Non-persistent mode opens 4 TCP connections instead of 1, so it pays 3 extra handshakes (3 RTT). With a cold cache each new client connection also means a new proxy→origin connection, another 3 RTT.
- Warm cache: predicted Δ ≈ 3 × 6.45 = **19.36 ms**; measured median Δ = 59.96 − 32.86 = **27.10 ms** (the rest: closing each connection and thread start-up at the proxy).
- Cold cache: predicted Δ ≈ 6 × 6.45 = **38.72 ms**; measured mean Δ = 113.04 − 67.38 = **45.66 ms** (median Δ 43.62 ms).
- In every mode the 4 page objects are tiny (29–179 B), so transmission is negligible and the page fetch time is almost entirely a count of round trips: that is why reusing the connection matters.

**Queueing.** Queueing is the only component that varies from run to run, so it shows up as the spread. The coefficient of variation ranges from 5.1 % to 108.7 % (Page fetch (4 objects), persistent, warm cache). The 2.4 GHz channel is shared with neighbouring networks, so a frame sometimes waits for the medium or is retransmitted; those runs are the outliers.

## 6. Sustainability and efficiency (Section 7)

**Measured on the wire** (tshark on H3, client↔proxy link, warm cache, every byte of every frame):

| Scenario | TCP connections | Frames | Bytes on wire | CNTP bytes |
|---|---|---|---|---|
| page, persistent | 1 | 15 | 1,986 | 1,152 |
| page, non-persistent | 4 | 36 | 3,162 | 1,122 |
| object /large.txt | 1 | 93 | 205,201 | 200,166 |
| object /index.html | 1 | 9 | 721 | 211 |

**Connection reuse.** A page view costs 1,986 B persistent vs 3,162 B non-persistent: saving **1,176 B = 37.2 %** per page view and 21 fewer frames. Each avoided connection is ≈392 B (SYN, SYN-ACK, ACK, FIN, ACK, FIN, ACK = 7 control frames).

**Cache hit.** A hit removes the whole proxy↔origin exchange: about 205,201 B for /large.txt and 139 B of CNTP (≈721 B on the wire with its TCP connection) for index.html. Over the whole client→proxy→origin path, a hit halves the bytes carried (one link instead of two) and removes all load from the origin.

**Projection.** Assume a campus of **10,000 users**, each loading this page 50 times and downloading a ~200 KB file 2 times a day, through one proxy with the measured hit ratio of **97.1 %** (TTL 60 s).
- Origin-link traffic without the cache: 10,000 × (50 × 1,986 B + 2 × 205,201 B) = 5,097.02 MB/day = 1,860.41 GB/year.
- With the cache: × (1 − 0.971) = 147.81 MB/day. Saved: **4,949.21 MB/day = 1,806.46 GB/year (97.1 %)**.
- Connection reuse on the client links: 10,000 × 50 × 1,176 B = **588.00 MB/day = 214.62 GB/year** and 10.50 million fewer frames per day for hosts and the AP to process.
- Energy: at 0.006–0.06 kWh/GB for network transmission (Aslan et al. 2018 give 0.06 kWh/GB for 2015, falling about 2× every two years), 2,021.08 GB/year ≈ **12.1–121.3 kWh/year**.
- Honest scale: our objects are tiny, so the absolute numbers are small. The percentages are what transfer: the cache saving (≈ hit ratio) applies to any object size, while the connection-reuse saving is a fixed ≈392 B per avoided connection, so it matters most for pages made of many small objects and shrinks to <1 % for large ones. Fewer frames also means less radio airtime, which is what drains battery on Wi-Fi clients.

**Text vs binary headers (compactness vs readability).** A CNTP response header is ≈111 B of text. A binary equivalent (1 B status, 4 B length, 1 B type, 4 B Max-Age, 1 B flags) would be ≈11 B. For index.html (29 B body) the text header is 79.3 % of the message and binary would save 71.4 %; for /large.txt the saving is 0.050 %. We kept text: the saving only matters for tiny objects, and the TCP/IP headers (54 B per frame) and the 7 handshake frames already cost more than the text does.

## 7. Caching freshness vs traffic reduction (Section 6)

Same request sequence for every TTL (seed 327, page views every 2.0 s on average for 120 s, each fetching the 4 objects). Model: each object is requested at rate λ = 0.5 /s; after a miss the copy stays fresh for T seconds and collects λT hits on average, so hit ratio ≈ λT / (1 + λT). Worst-case staleness = T (an update at the origin can stay invisible for a full TTL).

| TTL = Max-Age (s) | Requests | Hits | Hit ratio | Model λT/(1+λT) | Bytes from origin | Origin traffic saved | Median page fetch (ms) | Worst staleness (s) |
|---|---|---|---|---|---|---|---|---|
| 0 | 276 | 0 | 0.0 % | 0.0 % | 58,788 | 0.0 % | 68.978 | 0 |
| 5 | 276 | 207 | 75.0 % | 71.4 % | 14,628 | 75.03 % | 40.62 | 5 |
| 30 | 276 | 260 | 94.2 % | 93.8 % | 3,424 | 94.18 % | 42.55 | 30 |
| 60 | 276 | 268 | 97.1 % | 96.8 % | 1,712 | 97.09 % | 40.971 | 60 |
| 120 | 276 | 272 | 98.6 % | 98.4 % | 860 | 98.54 % | 37.7 | 120 |

**Diminishing returns.** 0→5 s: +75.0 points of hit ratio for +5 s of possible staleness; 5→30 s: +19.2 points of hit ratio for +25 s of possible staleness; 30→60 s: +2.9 points of hit ratio for +30 s of possible staleness; 60→120 s: +1.5 points of hit ratio for +60 s of possible staleness. Most of the traffic saving arrives with the first few seconds of TTL; after that each extra second of staleness buys almost nothing. Page fetch time drops as soon as objects are cached at all, then stays flat, because a hit is a hit whatever the TTL.
With TTL 120 s the run lasted only 120 s, so only the first (cold) request for each object missed; in a longer run the hit ratio would settle at the model value.
**Position.** The origin sends Max-Age 60 s by default: 97 % of origin traffic is removed while an update is visible within a minute, which suits mostly static pages. Content that changes often should get a short Max-Age (5 s still saves 75 %), and PURGE gives an immediate refresh when the content owner knows an object changed.
